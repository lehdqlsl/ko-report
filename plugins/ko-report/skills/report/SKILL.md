# report: 한국어 업무 보고서

**목표는 읽는 사람이 1분 안에 결론과 할 일을 아는 것이다.** 디자인은 `templates/report.css` 하나로 고정되고 원고에서 바꿀 수 없다. 글은 짧게, 표와 그림으로 보여 준다.

스크립트 경로는 이 스킬 폴더 기준이다(`<skill>/scripts/...`). 원고와 결과물은 사용자의 작업 폴더에 둔다.

## 1. 계약 잠그기 (한 줄로 말하고 바로 진행)

여섯 가지를 요청에서 추론해 사용자에게 한 줄로 알린다. 되묻는 것은 두 개 이상이 정말 불분명할 때 한 번만.

| 항목 | 값 |
|---|---|
| 종류 | progress(진행) · completion(완료) · qa(시험) · proposal(제안·결정 요청) · analysis(분석) · incident(장애) · policy(정책·규칙) · spec(화면설계서·스토리보드·화면 모음) |
| 독자 | internal(팀 안) · external(고객사·외부). external 이면 대외 금칙 검사가 켜진다 |
| 결론 | 이 보고서로 독자가 알아야 할 한 가지와 해야 할 일 |
| 기준 | 수치의 기준(어느 서버·판·시점). `basis` 에 적는다 |
| 형식 | HTML 한 파일(기본). 산출물로 낼 때는 같은 HTML 을 `pdf.py` 로 A4 PDF |
| 레이아웃 | doc(기본, A4 한 단) · web(넓은 화면용: 왼쪽 목차, 큰 첫 화면, 두 단). 화면으로 돌려 읽는 긴 문서만 web. PDF 는 어느 쪽이든 같다 |

종류 고르기: 보고가 아니라 규칙을 정해 두는 문서는 policy, 화면 그림이 본문인 문서는 spec. 억지로 proposal·analysis 에 넣지 않는다. spec 은 화면설계서(`:::screen` + 요소 표), 스토리보드(`:::scene` 장면), 화면 모음을 모두 담고 `label:` 로 머리 표시("화면설계서", "스토리보드")를, `numbering: off` 로 절 번호를 끈다(화면 번호와 겹치지 않게).

예: "QA 보고 · 내부용 · 결론은 '결함 4건 모두 수정, 남은 확인 2건' · 기준 스테이징 서버 v1.4.2 로 쓰겠습니다."

## 2. 재료 모으기

- 사실만 쓴다. 숫자·날짜·이름은 출처에서 그대로 옮긴다. 없으면 지어내지 말고 `[확인 필요: 무엇]` 으로 둔다.
- 빈칸이 생기면 한 번에 표로 모아 사용자에게 알린다(완료 보고 3번).
- QA 는 캡처가 증거다. `scripts/capture.py` 로 찍거나 이미 있는 캡처를 쓴다(`references/qa.md`). 코드만 읽어 검수했으면 `evidence: code` 로 두고 증거에 코드를 넣는다. 캡처를 지어내지 않는다.
- spec 은 화면마다 캡처 한 장이 기본이다. 떠 있는 배지·고정 머리는 `capture.py --hide`·`--unstick` 으로 치운다.

## 3. 원고 쓰기

1. `types/<종류>.md` 를 작업 폴더에 복사해 `<주제>_<YYMMDD>.md` 로 이름 붙인다. 틀의 절 순서를 지킨다.
2. `references/writing.md` 의 규칙대로 쓴다. 핵심:
   - **첫 절은 결론.** 숫자 타일 2~4개 + 3줄 이내(판단, 가장 큰 결과·문제, 다음 할 일). 정책·화면 설계에서 셀 수 있는 숫자가 없으면 타일 없이 3줄만. 숫자를 지어내지 않는다.
   - **"(없으면 지움)" 절은 내용이 없으면 지운다.** 틀의 `<…>` 자리표시자가 남으면 check.py 오류.
   - **절마다 표 하나 또는 5줄 이내.** 길어지면 표로 바꾼다.
   - **제목은 내용이 보이게.** "현황", "검토 결과" 같은 빈 제목 금지.
   - **선택지·중요도는 실제로 고를 게 있는 곳에만.** 모든 항목에 달지 않는다.
   - **수치에는 기준을 붙인다.** 어느 서버·언제·무엇 대비.
   - **말투는 개조식 명사형("수정 완료", "확인 필요"), 이어지는 문장만 "~습니다".** "~했다·~였다"는 쓰지 않는다.
3. 그림·표·상태는 `references/components.md` 의 블록으로 넣는다. HTML·style 을 원고에 직접 쓰지 않는다. 흐름은 `:::steps`, 추이·비중은 `:::chart`, 화면은 `:::screen`, 장면은 `:::scene`, 흐름도·구성도는 SVG 그림. 화면 문구 인용은 따옴표나 `코드`로 감싼다(문체 검사에서 빠진다). 긴 절 제목은 `## 제목 | 목차 이름`.

## 4. 다듬기 (산문이 많을 때만)

표와 개조식은 그대로 두고, 3문장 넘는 산문 문단이 있을 때만 그 문단을 `/humanize` (im-not-ai, light) 로 다듬는다. 윤문 뒤 숫자·고유명사가 바뀌지 않았는지 원고와 대조한다. 개조식을 문장으로 풀어 길게 만들면 되돌린다.

## 5. 검사·빌드·눈으로 확인

```bash
S=<skill>/scripts
python3 $S/check.py 원고.md                                          # external 이면 대외 금칙까지
uv run --with markdown --with pillow python $S/build.py 원고.md -o 원고.html
uv run --with playwright python $S/preview.py 원고.html               # 1280·390 전체 캡처 + 깨짐 검사
uv run --with playwright --with pypdf --with pypdfium2 python $S/pdf.py 원고.html --pngs   # 산출물로 낼 때
```

1. `check.py` 가 `READY` 가 될 때까지 원고를 고친다. ERROR 는 반드시, WARN 은 읽고 판단, GAP 은 사용자에게 알린다. 규칙을 느슨하게 바꿔 통과시키지 않는다. 결과 줄의 "보이는 글자·표 행"이 종류별 상한을 넘으면 부록으로 빼거나 문서를 나눈다.
2. `preview.py` 가 `<이름>_preview/` 에 1280px·390px 전체 캡처를 남기고 가로 넘침, 화면 밖 요소, 세로로 쌓인 좁은 표 칸을 WARN 으로 알린다. WARN 이 없어도 두 그림을 Read 로 직접 열어 본다: 잘린 표, 캡처 크기, 빈 절, 딱지 오용. web 레이아웃이면 `--dark` 로 어두운 화면도 한 번.
3. PDF 를 냈으면 `pdf.py` 의 쪽 품질 줄을 본다. 경고 셋: 마지막이 아닌 쪽이 60% 미만으로 참(큰 덩어리가 다음 쪽으로 넘어간 자리), 마지막 쪽이 12% 미만(거의 빈 쪽), 쪽 수가 종류별 예산 초과(진행·완료·장애 3, 제안·분석 5, QA 6, 정책 12, 설계 12 또는 그림 수 × 0.6 + 2 중 큰 쪽). `<이름>_pages/` 의 쪽 그림도 열어 표·캡처가 쪽 경계에서 잘리지 않았는지 본다.
4. 고칠 것은 원고에서 고친다(CSS 를 만지지 않는다). 큰 빈자리는 덩어리를 쪼개거나(긴 표를 두 표로, 캡처 묶음을 나눔) 순서를 바꿔 메운다.

## 6. 완료 보고

사용자에게 넷만 말한다.
1. 결과 파일 경로
2. `check.py` 판정(오류·경고 수)
3. `[확인 필요]` 빈칸 목록과 내가 세운 가정
4. 화면 확인 결과(preview·쪽 품질 경고와 직접 본 것). 캡처를 못 봤으면 "빌드 확인, 화면 미확인"이라고 쓴다

## 디자인을 바꾸고 싶을 때

색·글꼴·간격은 `templates/report.css` 한 곳에서만 바꾸고, 모든 종류의 예시를 doc·web 두 레이아웃과 PDF 로 다시 빌드해 확인한다. 보고서 하나만을 위해 스타일을 바꾸지 않는다.

## 쓰지 않는 경우

한 페이지 브리핑, 슬라이드, 엑셀·워드 파일 요청, 대화로 답하면 충분한 짧은 보고.
